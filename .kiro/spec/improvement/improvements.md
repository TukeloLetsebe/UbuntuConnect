# UbuntuConnect Improvements — Implementation Plan

## Problem Statement
UbuntuConnect works but needs security hardening and feature depth: two-stage verification (email + identity), structured onboarding, richer dashboards, a real fundraiser lifecycle, file uploads, notifications + email, post moderation, and UI/UX polish. Anti-fraud/AML is central: unverified individuals can view but not transact.

## Stack (source of truth = code)
- Backend: .NET 10, EF Core, SQL Server, JWT auth. Idempotent raw SQL migrations in `database/migrations` (currently up to 024; new ones start at 026+, follow the existing `IF NOT EXISTS` pattern and `USE UbuntuConnect_DB; GO`).
- Frontend: React 18, Vite 6, Tailwind 4, react-router 7, axios. Already installed and reusable: `react-slick` + `embla-carousel-react` (sliders), `input-otp` (codes), `@radix-ui/react-select` (dropdowns), `react-hook-form`, `recharts`, `sonner` (toasts), `date-fns`.
- Likely new deps: `libphonenumber-js` (frontend phone validation, optional), `SixLabors.ImageSharp` (backend image compression), `FaceONNX` + ONNX Runtime (Phase 4b; EmguCV optional for preprocessing) — all validated as real, free, .NET-compatible.

## Key Decisions
- Foundations-first sequencing (shared reusable services before features).
- Email behind `IEmailService`, dev mock now (logs/stores token), real SMTP later via config only.
- File storage behind `IFileStorageService`, local folder now, Azure Blob later via config/class swap. DB stays URL-string based (no schema churn to media fields).
- Card simulation: fake form with Luhn + expiry format checks, always approves, never contacts a bank.
- Reports: NPO (stakeholders), Business (statement evidence), Admin (oversight: who donated to whom); Individual keeps existing "View My Impact".
- Two verification gates for Individuals: (1) email verification unlocks login + view; (2) identity verification unlocks donate/topup/withdraw/impact/volunteer.
- Identity verification has two USER-CHOSEN routes (no automatic fallback): (a) admin manual review, or (b) local self-service face scan using FaceONNX. If a face scan fails, the user may retry or switch to the admin route.
- Liveness detection is explicitly OUT OF SCOPE. The face engine is optional via a config flag so it can be disabled near the deadline without breaking anything (falls back to admin-only).
- Remove public Admin registration; admins created via secure server-side seed/script only.
- Ghost account cleanup for unverified/inactive accounts (soft-delete first, dry-run mode).

## Grounding Facts (verified in code)
- `AuthController.Register` already enforces email uniqueness (app check + DB UNIQUE on `Users.UserEmail`). Gaps: no password confirmation, no email verification, no format validation, and it currently accepts `UserType == "Admin"` from the public form. There is a stray duplicate `AuthController.cs` at repo root; the live one is under `Controllers/`.
- No email, notification, or file-upload infrastructure exists anywhere. `Post.MediaUrl`, `Verification` certificates, and `VolunteerApplication` ID/face columns are all URL strings.
- Fundraisers are `Projects` (migration 024 added `TargetAmount`/`RaisedAmount`/`Images`). `RaisedAmount` is NEVER incremented by donations. No deadlines, no auto-close, no background jobs.
- `ReportController` produces donation CSV — it is NOT post-reporting. No post-abuse/report feature exists.
- Individual ID/face columns currently live on `VolunteerApplication`, not `Individual`. Per decision, individual KYC belongs on the `Individual` entity.
- `Users` has `IsVerified` (migration 002) and `IsActive` (migration 020). Verification approval flips `User.IsVerified`.
- Donate + TopUp live in `IndividualController`; Withdraw lives in `TransactionController`; `WalletController` only exposes balance. No amount limits (only > 0). No card/payment simulation.
- Volunteer accept/reject endpoints exist (NPO-only, ownership-checked) but only mutate Status — no notification/email.
- Frontend routes: role-guarded dashboards for NPO/Individual/Business/Admin via `ProtectedRoute`. Services: adminService, businessService, individualService, npoService; auth in `context/AuthContext.tsx`; axios in `lib/api.ts`.

## Identity Verification Flow
Register (password twice) -> account created IsVerified=false -> email token sent (mock) -> if email not verified: log in + VIEW only -> if verified: account active -> user CHOOSES identity route:
- Admin review route: upload ID + selfie -> admin approves/rejects.
- Face scan route: upload ID + webcam selfie -> FaceONNX compares -> high score auto-approves; low score/no face = failed, user retries or switches to admin route.
Both routes end at: fully verified -> unlock donate/topup/withdraw/impact/volunteer.
